# HJM 后续路线图

这份路线图的目标很简单：让 HJM 在保留“三进制 / 哈基米编码”特色的同时，逐步向以太坊式的完整节点网络靠近。

## 当前基线

Phase 0 已完成：

- 节点可以通过 P2P WebSocket 连接。
- 节点握手会检查 `chainId`、哈气值、挖矿奖励、签名方案。
- 链数据可以通过 `--data-dir` 保存和恢复。
- 用户可以本地签名，再用 `hjm_sendRawTransaction` 提交交易。
- 仓库里已有 Dockerfile、Docker Compose 和部署文档。

这意味着 HJM 已经不是单纯的本机 demo，而是可以在多台机器上启动多个节点，形成一个小型教学网络。

## Phase 1：真实部署可用

目标：四台 VPS 可以稳定互连，RPC 不要求用户把私钥交给服务器。

要做：

- 公网 RPC 模式：只开放查询、nonce、receipt、storage、peer 和 `hjm_sendRawTransaction`。
- VPS 部署模板：提供 `.env` 示例、单节点 Compose 示例、四节点启动步骤。
- systemd 运行方式：不用 Docker 时也能作为后台服务运行。
- 基础运维检查：健康检查、日志查看、重启恢复、peer 连接检查。

完成标准：

- 一台节点重启后能恢复已有链。
- 四台节点互相连接，至少一个节点挖出的块可以同步到其他节点。
- 公网 RPC 不能调用 `hjm_transfer`、`hjm_importWallet`、`hjm_newWallet` 这类私钥相关方法。

## Phase 2：网络安全加固

目标：公开节点不至于被简单刷爆或被垃圾 peer 拖垮。

要做：

- RPC 限流和请求体大小限制。
- P2P 连接数量限制、消息大小限制、重复消息抑制。
- peer 封禁/冷却机制。
- Cloudflare Tunnel / Nginx 反代样例。
- 只允许指定 IP 访问私有 RPC 的样例。

完成标准：

- 公开 RPC 和私有 RPC 有清楚边界。
- P2P 节点能拒绝明显异常连接和异常消息。
- 文档能解释 Cloudflare CDN 适合 RPC，不适合直接代理 P2P 共识连接。

## Phase 3：更像以太坊的执行层

目标：把 HJM VM 从“能跑合约演示”推进到更明确的执行模型。

要做：

- 明确账户模型：普通账户、合约账户、nonce、余额、storage。
- 明确交易类型：转账、部署、调用。
- 明确 receipt：状态、gas 使用、日志、合约地址。
- 增强 VM 指令集：算术、条件跳转、storage、事件日志。
- 给每条指令定义 gas 成本。

完成标准：

- 合约执行失败时不会破坏状态。
- receipt 可以解释一笔交易到底发生了什么。
- 文档能把 HJM VM 和 EVM 的相似/不同讲清楚。

## Phase 4：三进制特色深化

目标：不要只是在字符串上“哈基米化”，而是让三进制成为系统设计的一部分。

要做：

- 梳理普通 ternary `0/1/2` 与 balanced ternary `-1/0/1` 的设计取舍。
- 设计可选的 trit 编码层，让地址、哈希、VM 数据都能解释成 trit 序列。
- 尝试三进制 VM 指令或三值逻辑 opcode。
- 文档增加“三进制从编码到执行”的完整章节。

完成标准：

- 用户能看懂：哪里是编码特色，哪里是真正的三进制计算特色。
- 不破坏现有交易、地址和区块兼容性。

## Phase 5：共识机制升级

目标：从“教学 PoW”走向更明确的共识实验。

可选方向：

- 继续 PoW：提高难度调整、区块时间、孤块处理、最长链规则。
- 学以太坊 PoS：实现验证者集合、质押、slot/epoch、区块提议。
- 做 HJM 特色共识：围绕哈气值、trit 权重或教学可视化设计。

完成标准：

- 能解释节点为什么接受某条链、拒绝另一条链。
- 多节点同时出块时，网络最终能收敛。

## Phase 6：开发者体验

目标：让别人不只看 demo，而是真的愿意写合约、发交易、跑节点。

要做：

- SDK：封装本地签名、RPC 调用、合约部署和调用。
- 区块浏览器：看区块、交易、账户、receipt、peer。
- 合约示例：计数器、留言板、简单 token。
- Faucet：测试网水龙头。

完成标准：

- 新用户只看文档就能创建钱包、领测试币、部署合约、查询结果。

## 当前优先级

现在最应该先做 Phase 1 和 Phase 2 的交界处：

1. 把公网 RPC 模式做成代码里的硬限制。
2. 写四台 VPS 的部署说明。
3. 加 RPC/P2P 的基础防滥用保护。
4. 再考虑 VM 和共识升级。

原因是：只要节点要上公网，私钥安全和节点可用性必须先解决。VM 和共识很重要，但它们可以在一个更稳定的网络底座上慢慢演进。
